# Incus 프로젝트

Incus 는 LXD 에서 갈라져 나온 시스템 컨테이너 및 가상머신 관리자이다. 하나의 Incus 서버에서 여러 컨테이너와 가상머신을 운영하다 보면, 용도별로 인스턴스와 설정을 나눠서 관리하고 싶어진다. 이럴 때 사용하는 기능이 **프로젝트(project)** 이다.

이 글에서는 Arch Linux 에 Incus 가 이미 설치되고 초기화(`incus admin init`)된 상태를 가정하고, 다음 작업을 순서대로 진행한다.

- 새 프로젝트 만들기
- 일반 사용자(non-root)가 새 프로젝트에 접근할 수 있도록 trust 설정 수정하기
- Btrfs 스토리지 풀 만들기
- 기존 네트워크 확인하기
- 새 프로젝트의 기본(default) 프로파일 설정하기
- 프로젝트 전환과 테스트 컨테이너로 검증하기

> 이 글의 명령은 공식 문서를 기준으로 정리한 **예시 절차**이며, 출력 결과는 Incus 버전과 환경에 따라 다를 수 있다. 출력 예시가 아닌 설정 예시만 싣고, 실제 실행 결과는 각자의 환경에서 확인하도록 한다.

## 1. 프로젝트란 무엇인가

프로젝트는 하나의 Incus 서버를 **논리적으로 나누는 단위**이다. 각 프로젝트는 자신만의 인스턴스 목록을 가지며, 설정에 따라 이미지, 프로파일, 스토리지 볼륨, 네트워크 등을 프로젝트별로 분리할 수 있다.

프로젝트를 나누면 다음과 같은 점이 편해진다.

- 용도(예: 일반 작업용, GUI 앱용)별로 인스턴스 목록을 깔끔하게 분리할 수 있다.
- 같은 이름의 프로파일(예: `default`)을 프로젝트마다 다르게 구성할 수 있다.
- 프로젝트마다 다른 스토리지 풀을 기본으로 사용하게 만들 수 있다.
- 특정 사용자(인증서)가 접근할 수 있는 프로젝트를 제한할 수 있다.

### 1-1. 구성 요소 사이의 관계

| 구성 요소 | 범위 | 역할 |
|-----------|------|------|
| 프로젝트 (project) | 서버 안의 논리 구역 | 인스턴스·프로파일 등을 묶는 단위 |
| 프로파일 (profile) | 프로젝트별 (`features.profiles=true` 일 때) | 인스턴스에 적용할 설정과 디바이스 묶음 |
| 스토리지 풀 (storage pool) | 서버 수준 리소스 | 인스턴스 루트 디스크·이미지·볼륨이 저장되는 곳 |
| 네트워크 (network) | 기본적으로 `default` 프로젝트에서 상속 | 인스턴스의 NIC 가 연결되는 브리지 등 |
| 인스턴스 (instance) | 프로젝트별 | 컨테이너 또는 가상머신 |

여기서 중요한 점은 **스토리지 풀은 특정 프로젝트의 소유물이 아니라는 것**이다. 인스턴스가 어느 스토리지 풀을 쓸지는 프로파일(또는 인스턴스)의 `root` 디스크 디바이스가 `pool` 값으로 정한다. 네트워크도 마찬가지로 NIC 디바이스의 `network` 값으로 참조한다.

### 1-2. 이 글에서 사용하는 예시 구성

아래 이름은 모두 **설명을 위한 예시**이다. 실제 프로젝트, 스토리지 풀, 네트워크 이름은 각자의 환경에 맞게 바꿔서 읽으면 된다.

| 구성 요소 | 기존 프로젝트 | 새 프로젝트 |
|-----------|---------------|-------------|
| Project | `user-1000` | `user-1000-gui` |
| Profile | `default` | `default` |
| Storage pool | `default` | `mq_pool` |
| Network | `incusbr-1000` | `incusbr-1000` |

새 프로젝트 `user-1000-gui` 는 자신만의 `default` 프로파일을 가지고, 루트 디스크는 새로 만든 Btrfs 풀 `mq_pool` 에 두며, 네트워크는 기존 `incusbr-1000` 을 그대로 재사용한다. 다만 네트워크 재사용이 가능한지는 프로젝트의 네트워크 기능(`features.networks`)과 접근 제한(`restricted.networks.access`) 설정에 따라 달라진다. 이 부분은 [5. 기존 네트워크 확인](#5-기존-네트워크-확인)에서 다룬다.

[![Incus 프로젝트 구성도: 하나의 Incus 서버 안에 user-1000 과 user-1000-gui 프로젝트가 있고, 각 프로젝트의 default 프로파일이 서버 수준 리소스인 스토리지 풀(default, mq_pool)과 공유 네트워크 incusbr-1000 을 참조한다](/images/posts/incus/incus-project-overview.svg)](/images/posts/incus/incus-project-overview.svg)

### 1-3. 프로젝트 분리 ≠ 보안 격리

프로젝트는 기본적으로 **관리 단위의 분리**이다. 프로젝트를 나눴다고 해서 그 자체로 보안 경계가 생기지는 않는다.

- 프로젝트 안에서 무엇을 할 수 있는지(권한 있는 컨테이너, 호스트 경로 마운트, GPU 등 디바이스 사용)는 프로젝트의 `restricted` 및 `restricted.*` 설정으로 제한한다. 새로 만든 프로젝트는 기본적으로 `restricted` 가 꺼져 있다.
- 누가 어느 프로젝트에 접근할 수 있는지는 클라이언트 인증서(trust)의 `restricted` / `projects` 설정으로 제한한다.
- Unix 소켓으로 접속하는 root 및 `incus-admin` 그룹 사용자는 프로젝트와 관계없이 **항상 전체 권한**을 가진다.

즉, 실제 격리 수준은 "프로젝트 분리 + 프로젝트 제한 + 접근 제어"의 조합으로 결정된다.

## 2. 프로젝트 생성

현재 프로젝트 목록을 확인한다.

```bash
sudo incus project list
```

새 프로젝트는 다음 형식으로 만든다.

```bash
sudo incus project create <project-name>
```

이 글의 예시에서는 `user-1000-gui` 프로젝트를 만들고 설정을 확인한다.

```bash
sudo incus project create user-1000-gui
sudo incus project show user-1000-gui
```

### 2-1. 프로젝트 기능(features) 간단히 이해하기

`features.*` 값은 어떤 리소스를 **프로젝트 안에 따로 둘지**, 아니면 **`default` 프로젝트의 것을 상속해서 쓸지**를 정한다. 기능이 켜져(`true`) 있으면 해당 리소스가 프로젝트 안에 분리되고, 꺼져(`false`) 있으면 `default` 프로젝트의 리소스를 사용한다.

공식 문서 기준으로 `incus project create` 로 만든 프로젝트의 초기값은 다음과 같다.

| 기능 | 생성 시 초기값 | 의미 |
|------|----------------|------|
| `features.profiles` | `true` | 프로젝트 전용 프로파일 사용 |
| `features.images` | `true` | 프로젝트 전용 이미지 사용 |
| `features.storage.volumes` | `true` | 프로젝트 전용 커스텀 스토리지 볼륨 사용 |
| `features.storage.buckets` | `true` | 프로젝트 전용 스토리지 버킷 사용 |
| `features.networks` | `false` | `default` 프로젝트의 네트워크 상속 |
| `features.networks.zones` | `false` | `default` 프로젝트의 네트워크 존 상속 |

이 글에서 특히 중요한 두 가지는 다음과 같다.

- **`features.profiles=true`**: 새 프로젝트는 `default` 프로젝트의 `default` 프로파일을 쓰지 않는다. 그래서 새 프로젝트의 `default` 프로파일에는 루트 디스크나 NIC 같은 필수 디바이스가 없을 수 있고, 직접 채워 넣어야 한다. ([6장](#6-기본-프로파일-설정))
- **`features.networks=false`**: 새 프로젝트는 `default` 프로젝트에 정의된 네트워크를 그대로 사용한다. 참고로 `features.networks` 를 켜려면 서버에 OVN 이 구성되어 있어야 한다.

> 위 값은 생성 시점의 초기값이다. 설치 방식, 버전, `-c` 옵션 사용 여부에 따라 달라질 수 있으므로 반드시 `incus project show` 로 실제 값을 확인한다. 또한 `features.*` 는 프로젝트에 인스턴스가 없을 때만 변경할 수 있다.

## 3. 일반 사용자의 프로젝트 접근 권한 설정

### 3-1. 왜 필요한가

Incus 에 접근하는 방식은 여러 가지가 있다.

| 접근 방식 | 권한 |
|-----------|------|
| root 또는 `incus-admin` 그룹 (Unix 소켓) | 항상 전체 권한 |
| `incus` 그룹 + 멀티 유저 데몬 (incus-user) | 사용자별로 제한된 프로젝트 자동 생성 |
| 원격 TLS 클라이언트 인증서 | trust 설정에 따라 전체 또는 제한된 권한 |

이 글은 일반 사용자가 **제한된(restricted) 클라이언트 인증서**로 Incus 에 접근하는 환경을 가정한다. 예를 들어 `incus` 그룹 사용자를 위한 멀티 유저 데몬을 사용하면 사용자마다 제한된 프로젝트가 자동으로 만들어지는데, `user-1000` 처럼 UID 가 붙은 프로젝트 이름은 이런 환경을 가정한 예시이다.

제한된 인증서는 자신의 `projects` 목록에 있는 프로젝트에만 접근할 수 있다. 따라서 관리자가 `sudo` 로 새 프로젝트를 만들어도, 해당 인증서의 허용 목록에 새 프로젝트를 추가하기 전까지 일반 사용자는 새 프로젝트를 보거나 사용할 수 없다.

> 이 절차가 **모든 환경에서 필요한 것은 아니다.** `incus-admin` 그룹이나 root 로만 Incus 를 사용한다면 trust 설정을 바꿀 필요가 없다. 반대로 OIDC 나 별도의 인가(authorization) 설정을 쓰는 환경이라면 권한 관리 방법이 다르다.

### 3-2. 대상 인증서 찾기

신뢰된 인증서 목록을 확인한다.

```bash
sudo incus config trust list
```

목록에서 일반 사용자가 쓰는 인증서를 찾는다. 이름, 설명, 종류(`client`) 등으로 후보를 고른 뒤, 상세 내용을 확인해서 `restricted: true` 이면서 `projects` 에 기존 프로젝트(`user-1000`)가 들어 있는지 확인한다.

```bash
sudo incus config trust show <fingerprint>
```

### 3-3. 허용 프로젝트 목록에 새 프로젝트 추가하기

인증서를 편집한다.

```bash
sudo incus config trust edit <fingerprint>
```

편집기가 열리면 **기존 내용은 그대로 두고** `projects` 목록에 새 프로젝트만 추가한다.

```yaml
# name, type, certificate, description 등 다른 필드는 수정하지 않는다.
projects:
  - user-1000
  - user-1000-gui
restricted: true
```

수정할 때 주의할 점은 다음과 같다.

- **기존 프로젝트를 지우지 않는다.** `projects` 목록에서 `user-1000` 을 빠뜨리면 기존 프로젝트에 접근할 수 없게 된다. 목록이 비어 있으면 어떤 프로젝트에도 접근할 수 없다.
- **`restricted: true` 를 유지한다.** 권한 문제를 해결하려고 `restricted: false` 로 바꾸면 해당 인증서가 서버 전체에 대한 관리자 권한을 얻게 된다. 필요한 것은 권한 수준 상승이 아니라 허용 프로젝트 목록 변경이다.
- **`certificate` 값은 건드리지 않는다.** 인증서 내용이나 지문(fingerprint)을 블로그, 이슈, 채팅 등에 붙여 넣지 않도록 주의한다.

[![프로젝트 접근 권한 변경 전후 비교: 변경 전에는 restricted 인증서가 user-1000 에만 접근 가능하고, 변경 후에는 같은 restricted 인증서가 user-1000 과 user-1000-gui 모두에 접근 가능하다. restricted 값은 그대로 유지된다](/images/posts/incus/incus-trust-access.svg)](/images/posts/incus/incus-trust-access.svg)

일반 사용자 계정에서 `sudo` 없이 프로젝트 목록을 확인해 본다. `user-1000-gui` 가 보이면 접근 권한 설정이 된 것이다.

```bash
incus project list
```

### 3-4. 인증서 제한과 프로젝트 제한의 차이

두 설정은 이름이 비슷하지만 역할이 다르다.

| 구분 | 설정 위치 | 제한하는 것 |
|------|-----------|-------------|
| 인증서 제한 | `incus config trust edit` 의 `restricted`, `projects` | **어느 프로젝트에** 접근할 수 있는가 |
| 프로젝트 제한 | `incus project set` 의 `restricted`, `restricted.*` | 프로젝트 안에서 **무엇을** 할 수 있는가 |

제한된 인증서 사용자는 서버 전역 설정이나, 접근 가능한 프로젝트의 제한(restrictions)·한도(limits) 설정을 바꿀 수 없다. 하지만 새 프로젝트 `user-1000-gui` 는 기본적으로 `restricted` 가 꺼져 있으므로, 이 프로젝트 안에서는 권한 있는 컨테이너나 호스트 디스크 마운트 같은 설정도 가능하다. 여러 사람이 쓰는 서버라면 이 점을 반드시 고려해야 한다.

그렇다고 `restricted=true` 를 무조건 켜는 것도 정답은 아니다. 프로젝트 제한을 켜면 `restricted.devices.gpu` 는 기본값이 `block` 이 되고, 디스크 디바이스도 관리되는 스토리지 풀만 허용(`restricted.devices.disk=managed`)되는 등 GPU 패스스루나 호스트 경로 마운트가 막힐 수 있다. GUI 앱처럼 디바이스가 필요한 용도라면, 필요한 항목만 `allow` 로 열어 주는 식으로 개별 `restricted.*` 키를 검토하는 것이 좋다.

## 4. Btrfs 스토리지 풀 생성

### 4-1. 스토리지 드라이버 비교

Incus 는 여러 스토리지 드라이버를 지원한다. 공식 문서의 기능표를 바탕으로 간단히 비교하면 다음과 같다.

| 드라이버 | 특징 | 최적화된 이미지 저장·즉시 복제 | 참고 |
|----------|------|-------------------------------|------|
| `dir` | 일반 디렉터리 사용, 가장 단순 | 지원하지 않음 | 설정이 쉽지만 생성·스냅샷이 느릴 수 있음 |
| `btrfs` | Btrfs 서브볼륨·스냅샷 사용 | 지원 | 리눅스 커널 기본 포함, 쿼터는 qgroup 기반 |
| `zfs` | ZFS 데이터셋·스냅샷 사용 | 지원 | 기능이 풍부하고 쿼터가 엄격함, Arch 에서는 별도 커널 모듈 필요 |
| `lvm` | LVM 논리 볼륨(thin pool) 사용 | 지원 | 블록 디바이스 기반, 볼륨 전송 최적화는 미지원 |
| `ceph` | Ceph RBD 분산 스토리지 | 지원 | 여러 서버(클러스터)가 함께 쓰는 원격 스토리지 |

어느 드라이버가 일방적으로 우월한 것은 아니다. ZFS 는 개인 PC 에서도 많이 쓰이며 엄격한 쿼터가 필요하다면 더 나은 선택일 수 있다.

이 글에서 Btrfs 를 선택한 이유는 다음과 같다.

- Arch Linux 기본 커널에 포함되어 있고, 공식 저장소의 `btrfs-progs` 만 설치하면 된다.
- 스냅샷과 Copy-on-Write 를 이용해 이미지에서 컨테이너를 빠르게 만들 수 있다.
- 개인용 컨테이너 환경에서 별도 디스크 없이 루프 파일로 가볍게 시작하기 좋다.

### 4-2. 스토리지 풀 만들기

Btrfs 도구를 설치한다.

```bash
sudo pacman -S --needed btrfs-progs
```

`mq_pool` 이라는 이름으로 Btrfs 스토리지 풀을 만들고 확인한다.

```bash
sudo incus storage create mq_pool btrfs
sudo incus storage list
sudo incus storage info mq_pool
```

`source` 를 지정하지 않으면 Incus 는 **루프 파일(loop file)** 을 만들어 그 위에 Btrfs 파일 시스템을 구성한다. 공식 문서 기준 기본 크기는 "여유 디스크 공간의 20%, 최소 5GiB, 최대 30GiB" 이다. 루프 파일 방식은 간편하지만, 전용 파티션이나 디스크를 `source` 로 지정하는 방식보다 성능과 관리 면에서 불리할 수 있다.

### 4-3. (선택) 크기를 지정해서 만들기

처음부터 크기를 정하고 싶다면, **위의 생성 명령 대신** 다음 명령을 사용한다. 이미 `mq_pool` 을 만들었다면 같은 이름으로 다시 실행할 수 없다.

```bash
# 4-2 의 생성 명령 대신 사용하는 대안 (둘 중 하나만 실행)
sudo incus storage create mq_pool btrfs size=50GiB
```

이미 만든 루프 파일 풀의 크기를 늘리려면 생성 후에 별도로 `size` 값을 변경한다. 루프 파일 풀의 크기는 늘릴 수만 있고 줄일 수는 없다.

```bash
# 풀을 만든 뒤 크기를 늘릴 때 실행하는 별도 명령
sudo incus storage set mq_pool size=80GiB
```

### 4-4. Btrfs 사용 시 주의점

공식 문서는 Btrfs 드라이버에 대해 다음과 같은 제한을 안내한다.

- Btrfs 는 블록 디바이스를 직접 지원하지 않기 때문에, **가상머신(VM)** 디스크는 큰 이미지 파일로 저장된다. 이 방식은 효율이 떨어지고 스냅샷에서 문제가 생길 수 있다.
- qgroup 쿼터는 무작위 쓰기가 많은 VM 디스크 이미지에서 실제 사용량보다 빨리 한도에 도달할 수 있어, 공식 문서는 Btrfs 풀에서 VM 사용을 권장하지 않는다. 꼭 써야 한다면 루트 디스크의 `size.state` 를 루트 디스크 크기의 두 배로 설정하도록 안내한다.
- Btrfs qgroup 쿼터는 우회가 가능하므로, 엄격한 쿼터가 필요하면 다른 드라이버(예: ZFS)를 고려해야 한다.

이 글처럼 **컨테이너 중심**의 개인 환경이라면 Btrfs 로 충분하지만, VM 을 주로 쓴다면 다른 드라이버를 검토하는 것이 좋다.

## 5. 기존 네트워크 확인

새 프로젝트는 `features.networks=false` 이므로 `default` 프로젝트에 정의된 네트워크를 상속한다. 먼저 네트워크 목록과 기존 네트워크 설정을 확인한다.

```bash
sudo incus network list --project default
sudo incus network show incusbr-1000 --project default
```

`network show` 결과의 `used_by` 항목으로 이 네트워크를 참조하는 프로파일과 인스턴스를 확인할 수 있다.

새 프로젝트에서 이 네트워크가 실제로 보이는지는 프로젝트를 명시해서 확인한다. 일반 사용자 계정에서 실행하면 trust 설정까지 함께 확인할 수 있다.

```bash
incus --project user-1000-gui network list
```

여기서 `incusbr-1000` 이 보이지 않는다면 다음을 확인한다.

- 새 프로젝트에서 `features.networks` 가 켜져 있으면 `default` 프로젝트의 네트워크를 상속하지 않는다.
- 새 프로젝트에 `restricted=true` 를 설정했다면 `restricted.networks.access` 에 허용할 네트워크(예: `incusbr-1000`)를 지정해야 할 수 있다. 이 값이 비어 있으면 모든 네트워크에 접근할 수 있다.

네트워크 설정 자체를 바꾸고 싶다면 다음 명령으로 편집할 수 있다.

```bash
sudo incus network edit <network-name>
```

하지만 이 글처럼 **기존 네트워크를 그대로 재사용하는 경우에는 네트워크를 편집할 필요가 없다.** 브리지 설정을 잘못 바꾸면 기존 프로젝트의 인스턴스 통신에도 영향을 주므로, 필요할 때만 수정한다.

> 같은 네트워크를 공유한다는 것은 두 프로젝트의 인스턴스가 **같은 브리지에 연결된다는 뜻**이다. 프로젝트가 다르다고 해서 네트워크가 격리되지는 않으며, 같은 브리지의 인스턴스끼리는 서로 통신할 수 있다. 네트워크 격리가 필요하다면 별도 네트워크나 ACL 등을 따로 구성해야 한다.

## 6. 기본 프로파일 설정

### 6-1. 현재 프로파일 확인

새 프로젝트의 프로파일 목록과 `default` 프로파일 내용을 확인한다. 여기서부터는 일반 사용자 계정에서 `--project` 로 프로젝트를 명시해서 실행한다.

```bash
incus --project user-1000-gui profile list
incus --project user-1000-gui profile show default
```

새 프로젝트의 `default` 프로파일은 보통 다음처럼 디바이스가 비어 있다. (설정 예시이며 실제 출력과 다를 수 있다.)

```yaml
config: {}
description: Default Incus profile for project user-1000-gui
devices: {}
name: default
used_by: []
project: user-1000-gui
```

이 상태로는 새 인스턴스에 루트 디스크와 네트워크 인터페이스가 지정되지 않기 때문에, 인스턴스 생성 시 루트 디스크를 찾을 수 없다는 오류가 날 수 있다.

### 6-2. 프로파일 편집

프로파일을 편집한다.

```bash
incus --project user-1000-gui profile edit default
```

`devices` 에 NIC(`eth0`)와 루트 디스크(`root`)를 추가한다.

```yaml
config: {}
description: Default Incus profile for project user-1000-gui
devices:
  eth0:
    name: eth0
    network: incusbr-1000
    type: nic
  root:
    path: /
    pool: mq_pool
    type: disk
name: default
used_by: []
project: user-1000-gui
```

편집기 대신 명령으로 디바이스를 추가할 수도 있다. 위 YAML 편집과 같은 결과이므로 **둘 중 한 가지 방법만** 사용한다.

```bash
incus --project user-1000-gui profile device add default eth0 nic network=incusbr-1000 name=eth0
incus --project user-1000-gui profile device add default root disk path=/ pool=mq_pool
```

[![기본 프로파일 설정 전후 비교: 설정 전 devices 가 비어 있고, 설정 후 eth0 은 incusbr-1000 네트워크를, root 는 Btrfs 스토리지 풀 mq_pool 을 가리키며 새 인스턴스가 이 두 디바이스를 상속한다](/images/posts/incus/incus-profile-before-after.svg)](/images/posts/incus/incus-profile-before-after.svg)

### 6-3. 각 항목의 의미

| 항목 | 의미 |
|------|------|
| `eth0` | 디바이스 이름. 프로파일 안에서 디바이스를 구분하는 키 |
| `type: nic` | 네트워크 인터페이스 디바이스 |
| `network` | NIC 를 연결할 Incus 관리 네트워크 이름 (`incusbr-1000`) |
| `name` | 인스턴스 안에서 보이는 인터페이스 이름 (`eth0`) |
| `root` | 디바이스 이름. 관례적으로 루트 디스크에 사용 |
| `type: disk` | 디스크 디바이스 |
| `path: /` | 인스턴스 안의 마운트 경로. `/` 이면 루트 디스크 |
| `pool` | 루트 디스크를 만들 스토리지 풀 (`mq_pool`) |

프로파일 YAML 에서 직접 편집하는 대상은 `config`, `description`, `devices` 이다. `name`, `used_by`, `project` 는 프로파일을 식별하거나 사용 현황을 보여 주는 정보성 필드이므로 편집 대상이 아니다. (`default` 프로파일은 이름을 바꾸거나 삭제할 수 없다.)

정리하면, **스토리지 풀은 프로젝트가 소유하는 것이 아니라 프로파일의 `root` 디스크 디바이스가 선택하는 것**이다. 같은 `mq_pool` 을 다른 프로젝트의 프로파일에서 참조할 수도 있고, 인스턴스 단위로 다른 풀을 지정할 수도 있다.

### 6-4. 스토리지 풀 참조 확인

```bash
sudo incus storage list
```

프로파일을 저장한 뒤 `mq_pool` 의 `USED BY` 값이 늘어난 것을 볼 수 있다. 이 값은 해당 풀을 **참조하는 항목(프로파일, 인스턴스, 이미지, 볼륨 등)의 수**이다. 값이 늘었다고 해서 실행 중인 인스턴스가 늘었거나 디스크를 그만큼 사용했다는 뜻은 아니다. 지금 단계에서는 `default` 프로파일 하나가 참조를 추가했을 뿐이다.

## 7. 프로젝트 전환과 관리

### 7-1. 현재 프로젝트 전환

```bash
incus project list
incus project switch user-1000-gui
incus list
```

`incus project switch` 는 클라이언트 설정에 **현재 프로젝트를 저장**한다. 이후 `--project` 없이 실행하는 명령은 모두 `user-1000-gui` 를 대상으로 한다. `incus project list` 에서는 현재 프로젝트 옆에 `(current)` 표시가 붙는다.

### 7-2. 명령 단위로 프로젝트 지정

현재 프로젝트를 바꾸지 않고 특정 명령에서만 다른 프로젝트를 대상으로 할 수도 있다.

```bash
incus --project user-1000-gui list
```

| 방식 | 범위 | 어울리는 상황 |
|------|------|---------------|
| `incus project switch <name>` | 이후 모든 명령 (클라이언트 설정에 저장) | 한동안 한 프로젝트에서만 작업할 때 |
| `incus --project <name> ...` | 해당 명령 한 번 | 스크립트, 여러 프로젝트를 오가며 확인할 때 |

`sudo incus` 는 root 사용자의 클라이언트 설정을 사용하므로, 일반 사용자에서 `project switch` 를 해도 `sudo incus` 의 현재 프로젝트는 바뀌지 않는다. 헷갈린다면 `--project` 를 명시하는 습관이 안전하다.

## 8. 테스트 컨테이너로 검증하기

설정이 제대로 되었는지 테스트 컨테이너를 만들어 확인한다. 아래 명령은 **일반 사용자 계정에서 `sudo` 없이** 실행하는 것을 기준으로 한다(스토리지 볼륨 확인만 `sudo` 사용).

```bash
incus --project user-1000-gui launch images:ubuntu/24.04 test-ub
incus --project user-1000-gui list
incus --project user-1000-gui exec test-ub -- bash
incus --project user-1000-gui config show test-ub --expanded
sudo incus --project user-1000-gui storage volume list mq_pool
```

각 명령으로 확인할 내용은 다음과 같다.

| 확인 항목 | 확인 방법 |
|-----------|-----------|
| `sudo` 없는 프로젝트 접근 | `launch`, `list` 가 권한 오류 없이 실행되는지 |
| 인스턴스 생성 | `list` 에서 `test-ub` 가 `RUNNING` 상태인지 |
| 네트워크 구성 | `list` 에 IPv4 주소가 할당되었는지, 컨테이너 안에서 `ip addr` 로 `eth0` 이 보이는지 |
| 루트 스토리지 풀 | `config show --expanded` 의 `devices.root.pool` 이 `mq_pool` 인지 |
| 네트워크 연결 대상 | `config show --expanded` 의 `devices.eth0.network` 가 `incusbr-1000` 인지 |
| 스토리지 볼륨 | `storage volume list mq_pool` 에 `test-ub` 컨테이너 볼륨이 있는지 |

`config show --expanded` 는 프로파일에서 상속된 디바이스까지 펼쳐서 보여 주므로, 프로파일 설정이 인스턴스에 제대로 적용되었는지 확인할 때 유용하다.

### 8-1. (선택) 테스트 컨테이너 정리

검증이 끝났다면 예시 컨테이너를 삭제한다. 삭제한 인스턴스는 되돌릴 수 없으므로 이름을 꼭 확인한다.

```bash
incus --project user-1000-gui stop test-ub
incus --project user-1000-gui delete test-ub
```

## 10. 마무리

이 글에서 진행한 설정 흐름을 정리하면 다음과 같다.

1. `sudo incus project create` 로 새 프로젝트를 만든다.
2. 제한된 인증서를 쓰는 환경이라면, `restricted: true` 는 유지한 채 `projects` 목록에 새 프로젝트를 추가한다.
3. `btrfs-progs` 를 설치하고 Btrfs 스토리지 풀을 만든다.
4. 재사용할 네트워크가 새 프로젝트에서 보이는지 확인한다.
5. 새 프로젝트의 `default` 프로파일에 `eth0` NIC 와 `root` 디스크를 추가한다.
6. `project switch` 또는 `--project` 로 작업할 프로젝트를 고른다.
7. 테스트 컨테이너로 접근 권한, 스토리지 풀, 네트워크 설정을 검증한다.

이렇게 프로젝트를 나누면 기존 환경을 건드리지 않고 용도별로 인스턴스와 프로파일을 분리할 수 있고, 새 프로젝트의 인스턴스만 다른 스토리지 풀에 두는 것도 프로파일 한 곳에서 관리할 수 있다. 다만 프로젝트 분리는 관리 편의를 위한 것이고, 실제 보안 격리가 필요하다면 프로젝트 제한과 접근 제어, 네트워크 분리를 함께 설계해야 한다는 점을 기억하자.
